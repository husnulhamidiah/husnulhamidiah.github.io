How I Ended Up Writing a Java Wrapper for a Clojure Kafka Library

Husnul Anwari

6 Aug 2026

At GoPay, I work a lot with Kafka. We have a few standard libraries for consuming Kafka events, and one of them is Ziggurat.

As written in the README:

“Ziggurat is a framework built to simplify stream processing on Kafka. It can be used to create a full-fledged Clojure app that reads and processes messages from Kafka.”

It is a mature library. It has been battle-tested in production and comes with many convenient features.

The only problem for me is that it is written in Clojure.

I am not against Clojure. I actually enjoyed learning and using it. But if I have another JVM language available, I naturally prefer Java. It turns out I am not the only one. Many of my teammates feel the same way.

Whenever we need to create a new Kafka consumer, there is always a small moment of hesitation. We all know how to do it, but nobody is really excited because it means writing Clojure.

That made me curious.

If Clojure libraries can use Java libraries, why can’t Java use Clojure libraries?

Since both languages run on the JVM, I felt it should be possible.

So I started digging.

I spent hours reading documentation, browsing Stack Overflow, and going through many rounds of trial and error. Looking back, it was a lot of manual work. At that time, I did not even think about asking an AI assistant for help. I just kept experimenting until I finally found a way.

Those experiments eventually became Borobudur.

You can find the project here: Borobudur on GitHub.

Borobudur is a Java wrapper for Ziggurat. I intentionally kept it as a thin wrapper because my goal was simple. I wanted Java developers to consume Kafka events without having to write Clojure, so they could focus on the business logic instead.

Not every feature from Ziggurat has been tested through Borobudur yet. However, from what I have seen so far, supporting more features should be straightforward.

The best part is that Borobudur is no longer just a side project. It is now serving GoPay in production, and several Kafka consumers are already using it.

It is definitely not perfect, and there is still a lot to improve. But I am happy with where it is today. Something that started as a simple question became a tool that my team actually uses, and creating a new Kafka consumer in Java is no longer something we try to avoid.
